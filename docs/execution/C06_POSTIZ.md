# Configuration de publication — désactivée par défaut

**Aucun compte réel qualifié par cette livraison.** Ne pas activer le transport pour explorer la démo. Le calendrier et les ZIP manuels fonctionnent sans Postiz, clé de chiffrement ou worker. LinkedIn personnel / PNG carré ou portrait est le seul contrat d’envoi direct implémenté. Pages LinkedIn, autres formats, Instagram et TikTok : kit manuel. Ne pas accorder de permission pour une offre avec facturation marginale non plafonnée : les deux outils C05 déclarent zéro centime par appel, pas le coût d’un abonnement tiers.

## Préparation par un administrateur autorisé

- Appliquer les migrations dans l’environnement de qualification et générer le client Prisma. Utiliser le worker Hatchet C05 et **le même stockage local des artefacts** que le Studio. Le chemin C05 local ne lit pas de références S3. Aucune seconde file à installer.
- Fournir `PUBLISHING_ENCRYPTION_KEY` via le gestionnaire de secrets de l’API et du worker : 32 octets aléatoires encodés en base64. La clé n’est ni stockée en base ni retournée. Conserver une sauvegarde sécurisée ; changer cette clé sans rechiffrer les lignes les rend illisibles. Laisser `POSTIZ_PUBLISH_ENABLED` absent ou à `0` sur les deux processus par défaut.
- Après consentement explicite, associer **dans Postiz** le compte autorisé et identifier son `integration.id`. Session super-admin + CSRF : `POST /api/admin/publishing/connections` avec `ownerId`, `channel` (identifiant, pas nom affiché), `token` (clé d’API Postiz), `expiresAt` (date ISO de péremption locale) et `relayKey` (secret aléatoire distinct d’au moins 32 caractères). Ne pas mettre ces valeurs dans un ticket, URL ou journal. La destination ne peut pas être modifiée par la commande utilisateur. AES-GCM lie les deux secrets à l’identifiant de connexion et à leur usage. Pour renouveler le token : `PUT /api/admin/publishing/connections/:id/credential` avec `token, expiresAt`. Le propriétaire peut révoquer via `DELETE /api/publishing/connections/:id` ; cela efface les secrets locaux, mais **n’annule pas les publications déjà programmées chez Postiz**. Révoquer également le jeton chez le fournisseur.
- Accorder explicitement `postiz.schedule@1` et, si permis, `postiz.cancel@1` via la politique de compte C05. Activer `POSTIZ_PUBLISH_ENABLED=1` sur API et worker uniquement pendant une qualification autorisée. Sortie réseau : `https://api.postiz.com/public/v1` uniquement, sans redirection ni import depuis une URL utilisateur. Ne pas substituer un hôte fourni par un client.

## Du calendrier au reçu

1. Approuver le contenu éditorial. Dans le Studio, lier la création à cette version du calendrier, rendre et approuver la révision exacte. Une édition ultérieure nécessite une nouvelle liaison. Dans le calendrier, ouvrir le contenu pour voir médias, légende, CTA et date. L’export manuel fournit fichiers ordonnés, légende, manifeste SHA-256 et instructions ; limite 64 Mio.
2. Pour une date future et une destination compatible : choisir le compte, préparer, puis **autoriser**. Le worker vérifie le canal via `GET /integrations`, charge les octets scellés via `POST /upload`, puis envoie `POST /posts`. `SUBMITTED` signifie seulement « accepté par Postiz ». Lire la raison d’échec avant toute nouvelle action. Un refus de jeton ou de canal sans effet permet une nouvelle préparation après correction et exige une autre approbation. Une réponse perdue après émission reste `UNKNOWN` : **ne pas dupliquer le contenu pour réessayer**. Inspecter le compte et l’incident C05 hors bande. Sans preuve, garder l’état inconnu.
3. Une demande non prise en charge est retirable localement. Une programmation soumise peut faire l’objet d’une commande d’annulation distincte, approuvée (`DELETE /posts/:id`). Ce n’est pas une suppression de publication déjà en ligne. Actualiser le panneau pour relire le registre ; l’actualisation seule n’interroge pas le réseau.

## Relais de confirmation

`scripts/publishing/postiz-receipt.mjs` est un outil **opérateur**, pas une route publique de proxy. Après autorisation de lecture, fournir dans son environnement `VULULU_ORIGIN` (origine HTTPS de confiance, sans chemin), `POSTIZ_READ_TOKEN`, `VULULU_RELAY_KEY`, `CONNECTION_ID`, `CHANNEL_ID`, `REMOTE_POST_ID` (reçu de soumission) et `SCHEDULED_AT`. Exécuter `node scripts/publishing/postiz-receipt.mjs`. Le relais consulte `GET /posts` autour de la date prévue, vérifie ID, intégration, plateforme, état et `releaseId`. Une absence de ligne ou un identifiant `missing` n’est pas un succès. L’outil ne programme ni n’annule aucun post. Il peut être réexécuté pour la même preuve.

Pour un relais équivalent : `POST /api/publishing/relay` avec `{connectionId,timestamp,payload}` où `timestamp` est Unix en secondes et `payload` est **la chaîne JSON exacte** contenant `eventId` UUID stable, `remoteId`, `state` (`PUBLISHED` ou `FAILED`) et, pour `PUBLISHED`, `networkReceipt`. En-tête `X-Vululu-Signature: v1=<hex HMAC-SHA256(relayKey, connectionId + '.' + timestamp + '.' + payload)>`. Fenêtre de 5 minutes, comparaison à temps constant, déduplication persistante. En cas de livraison tardive, renouveler l’horodatage et la signature, pas l’identité de l’événement. Un 409 `receipt_not_yet_known` demande de vérifier la soumission ; ne pas créer de nouveau post. **Ce protocole est celui de Vululu**, pas une signature native promise par Postiz.
