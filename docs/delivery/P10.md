## 1. Périmètre livré

**Publication**
- Sélection d'une **révision approuvée** liée à une version de calendrier compatible (validation serveur existante : `approved_revision_required`, `calendar_changed`, `variant_missing`, `editorial_approval_required`, `caption_too_long`).
- **Légendes et hashtags éditables** : `calendar.variant.hashtags` additif (≤ 10, `#tag`, unicité insensible à la casse, défaut `[]`), éditeur par plateforme, validation locale actionnable, digest éditorial et légende publiée incluant les hashtags ; le paquet manuel hérite du même texte.
- **Compte et plateforme exacts** : le panneau affiche le réseau, le compte (`displayName`/`channel`), l'expiration/révocation, la révision et l'heure planifiée avant toute action.
- **Validation des exigences** : capacités plateforme (longueur de légende, formats programmables, annulation), éligibilité média, état éditorial et version de calendrier.
- **Programmation ou kit manuel** : `prepare` (direct) ou `package` (ZIP + caption.txt + manifest + instructions) ; aucune publication en mode drapeau off (`direct_disabled`).
- **Autorisation humaine explicite** : après préparation, l'opération `postiz.schedule@1` est autorisée par `POST /api/execution/:id/approve { digest }` ; l'état réel est affiché.
- **États exacts** : PREPARED / SENDING / SUBMITTED / CANCELLING / PUBLISHED / FAILED / UNKNOWN / CANCELLED, avec motifs ; « transféré » n'est jamais présenté comme « publié ».
- **Reçus et traçabilité** : nouvelle route `GET /api/publishing/:id` (demande, compte, reçu réseau, journal `PublicationEvent` id+horodatage, opérations de soumission/annulation).
- **Annulation / reprogrammation sûres** : annulation via l'opération existante, réconciliation, nouvelle tentative ; reprogrammation = annulation si soumis + modification de l'heure dans le calendrier (nouvelle version) + nouvelle préparation, expliquée dans l'UI.
- **Aide connexion** : état de clé expirée/révoquée et renvoi vers la surface existante « Comptes de publication » ; aucun flux OAuth inventé.

**Marketing**
- Offres confirmées, objectifs de campagne, ressources créatives et calendriers existants reliés : idées éditoriales (plan marketing), déclinaisons de légendes/CTA par plateforme, calendriers hebdomadaires/campagne, hashtags éditables.
- **Réutilisation** : les créations approuvées sont exposées dans les résultats avec lien vers le Studio (la reprise crée une nouvelle révision via `restore`, jamais un écrasement).
- **Suggestions de suivi** : suggestions déterministes du serveur dérivées uniquement des compteurs observés (contenus approuvés non programmés, envois incertains, échecs, absence de publication confirmée, absence de création approuvée).

**Résultats**
- Contenus **créés / approuvés / programmés / publiés** par état, publications par état, dont `publishedConfirmed` = `PUBLISHED` **avec reçu réseau**.
- **Source et horodatage** de chaque ensemble observé (`ContentItem`, `PublicationRequest`, `observedAt`) ; métriques fournisseur uniquement si `POSTIZ_ANALYTICS_ENABLED=1` et mesure datée, sinon « non disponible » (jamais de chiffre inventé).
- Regroupement par campagne et par projet, créations approuvées réutilisables, suggestions d'amélioration factuelles.
