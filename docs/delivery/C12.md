# C12 — Plateforme commerciale (test uniquement)

**Livraison :** pass prépayés à durée fixe, sans renouvellement automatique. Le catalogue initial est vide. Aucun prix, contrat commercial final, facture fiscale ni paiement réel n’est livré. `/account` présente les offres, les commandes et les deux soldes ; `/support` traite les tickets ; `/admin/commerce` complète les écrans utilisateurs, jobs, coûts, fournisseurs et audit existants.

## Activation contrôlée

1. Appliquer `20261120180000_commercial` après C11 et régénérer le client Prisma pour l’API **et** les workers. La migration conserve le comportement de démonstration : elle n’active pas la vente. Utiliser une base de recette dédiée, drainer les anciennes tâches avant la bascule.
2. Dans `/admin/commerce`, un `super_admin` enregistre la référence de l’accord du propriétaire, le tarif en unités mineures (EUR/USD/GBP), les jours, les fonctions, les deux plafonds et les unités par image/vidéo. Le modèle de règles `prepaid-v1` doit lui aussi être approuvé. Changer le prix exige une **nouvelle version de produit** ; masquer l’ancienne ne change pas les achats existants.
3. Après validation explicite, activer les contrôles sur cette base. L’interrupteur est persistant, global, sans désactivation par une route client. **Un achat n’autorise jamais à lui seul la dépense auprès d’un fournisseur** : les budgets, autorisations et consentements C05–C09 restent indépendants.
4. Pour une qualification Stripe autorisée, configurer côté API uniquement `STRIPE_TEST_SECRET_KEY` (`sk_test_…`), `STRIPE_TEST_WEBHOOK_SECRET` (secret de l’endpoint de test) et une `APP_ORIGIN` de confiance. SDK officiel `stripe@18.5.0`, Checkout hébergé, `mode=payment`, carte de test uniquement. La clé live et les événements live sont refusés. [Mode de test](https://docs.stripe.com/testing) · [signatures](https://docs.stripe.com/webhooks/signature) · [idempotence](https://docs.stripe.com/api/idempotent_requests).
5. Sur le compte de test dédié, adresser `payment_intent.succeeded`, `payment_intent.payment_failed`, `payment_intent.canceled`, `checkout.session.expired`, `charge.refunded`, `refund.failed` à `POST /api/billing/stripe-webhook`. Le proxy Next transmet le flux brut. La redirection du navigateur n’est jamais une preuve de paiement. Une ouverture incertaine réutilise la commande/la clé d’idempotence ; après la fenêtre de sécurité de 23 h, vérifier le tableau de bord Stripe, ne pas recréer automatiquement le paiement.

## Invariants financiers et récupération

| Situation | Comportement |
|---|---|
| Activation | Une commande propriétaire lie une seule version de produit, session et intention. Vérification SDK sur les octets reçus, fenêtre de 300 s, vérification de la devise, du montant encaissé et des références. Reçu minimal (ID, type, empreinte) et transition dans une transaction. Les doubles livraisons ne créent pas de nouveaux droits. |
| Conservation du solde | Par achat, `disponible = allocation − réservé − consommé`, uniquement si payé, non expiré et non suspendu. Les lots ne sont pas fusionnés : réserver dans le premier lot compatible ayant suffisamment d’unités, par date de fin. Pas d’emprunt entre création et média. Le verrou transactionnel porte sur le client, même s’il a plusieurs achats. |
| Création ordinaire | Rendu de master, job de production/correction, raffinement marketing par le fournisseur : une unité de création. Les brouillons restent libres ; l’aperçu commercial est réduit et marqué. Une version rendue ne peut pas être facturée deux fois par les chemins direct et broker. Relecture/téléchargement d’un master existant sans nouvelle consommation. |
| Média premium | Le crédit image/vidéo est réservé à l’approbation C05 ; le succès média exige un résultat `READY`. Une sortie invalide peut coûter au fournisseur sans consommer le crédit client. La publication vérifie une fonction de plan, pas un crédit média. Inspection et arrêt de publication ne demandent pas un nouvel achat. |
| Limite/expiration | Réservation refusée avant exécution si le lot est expiré, suspendu, gelé, épuisé ou sans la fonction. Le broker revérifie avant sa première invocation ; le job de production revérifie à l’entrée en exécution. Les traitements déjà lancés peuvent être finalisés. Les historiques, tickets et commandes de test restent consultables. |
| Échec/annulation | Annuler un travail en file libère sa réservation. Un paiement échoué ou une session expirée ne crédite rien. Un échec tardif ne supplante pas une réussite. Fermer une session Checkout attend une confirmation, ce n’est pas un remboursement. |
| Issue inconnue | Pas de nouvel appel automatique. Le coût fournisseur inconnu reste dans C05. Après rapprochement C05, une décision distincte, justifiée et auditée consomme ou libère le crédit client. Pour un job/rendu bloqué, la réparation vérifie le statut terminal du run ou le manifeste d’un rendu âgé de plus de 24 h ; sans preuve, la réservation reste visible. |
| Remboursement | L’opérateur décide et initie tout remboursement autorisé **dans Stripe test**, pas par un bouton Support. Le remboursement intégral retire le reliquat ; un partiel gèle le lot, même reçu avant la réussite. Pas de solde négatif ni de nouvelle allocation par replay. Un échec de remboursement impose un examen. L’admin peut relire l’intention et les remboursements terminés auprès de Stripe, sans saisir son propre total ; si les preuves manquent, les droits restent gelés. |

## Support, données et rétention

- `support` est un rôle distinct, provisionné par invitation admin. Il consulte les dossiers ordinaires et répond ou change leur statut. Il ne peut ni voir le cockpit financier, ni fixer un prix, suspendre un compte, rapprocher un crédit ou traiter une suppression. Un admin supervise mais ne se fait pas passer pour le répondant Support. Les contrôles sont côté serveur ; les mutations de catalogue, suspension, dossiers, rapprochements et suppression écrivent l’audit dans la transaction métier.
- Tickets et entrées de conversation sont persistants et horodatés. Un client ne voit que ses dossiers. Statut attendu avant écriture, dossier fermé non réinscriptible ; 20 dossiers ouverts maximum par client. Les dossiers fermés depuis 90 jours sont purgés au démarrage puis quotidiennement lorsque l’API tourne.
- Export par rubrique après mot de passe + session + CSRF, pages de 100 pour les collections ; pas de hachages, jetons, clés, pièces de paiement ou chemins de stockage. Les fichiers créatifs s’exportent par le Studio. L’export proposé n’est pas une copie brute de la base.
- La demande de suppression est authentifiée et révocable avant décision (clôture du dossier). Un admin différent du demandeur doit confirmer et justifier. Les comptes admissibles sont supprimés avec sessions et données dépendantes. Projets avec médias/runs, connexions externes, commandes ouvertes, pass actifs ou crédits réservés nécessitent un examen manuel : **dossier en cours, pas de fausse confirmation d’effacement**. Vérifier stockage externe, effets en cours, obligations de conservation et sauvegardes avant clôture. Pas de suppression automatique chez un prestataire tiers.
- Les commandes, reçus anti-rejeu et unités financières ne sont pas effacés par la purge des tickets. Après effacement admissible, leur clé de compte est pseudonyme, sans copie de l’adresse e-mail. Pas de webhook brut ni de données carte en base. Les références de preuve ne doivent contenir aucun secret. La durée légale de conservation, les règles fiscales et le cycle des sauvegardes devront être fixés par le propriétaire pour sa juridiction **avant** toute offre réelle.
